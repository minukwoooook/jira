# Jira 자율형 Dashboard — 설계 문서

> **이번 구현 범위: 로컬 개발 하네스 + DB 스키마 + 수집 파이프라인 + CLI**
> 쿼리 API(6장)와 UI는 설계만 해두고 구현은 다음 단계다.
>
> 개발은 사외(집)에서 하고 사내에서 적용한다. **Jira와 Oracle 모두 사내에만 있고 데이터
> 반출이 불가능하므로**, 검증 가능한 것과 불가능한 것을 나누는 것이 이 문서의 큰 축이다
> (11장).

## 1. 배경과 목표

여러 Jira Data Center 인스턴스(각기 다른 도메인)의 프로젝트 데이터를 Oracle DB로 수집해두고,
사용자가 X축·Y축·차트타입을 직접 골라 대시보드를 구성할 수 있게 하려 한다.

문제는 **Jira 프로젝트마다 필드 구성이 전부 다르다**는 점이다. 프로젝트별로 테이블을 만들면
새 프로젝트나 새 커스텀 필드가 생길 때마다 DDL이 필요해 운영이 불가능하다. 따라서 이 프로젝트의
핵심은 두 가지다.

1. **스키마 변경 없이 임의의 필드 구성을 수용하는 DB 구조**
2. **필드 카탈로그를 읽어 SQL을 동적으로 만드는 쿼리 엔진**

### 1.1 확정된 요구사항

| 항목 | 결정 |
|---|---|
| Jira 종류 | **Data Center 10.3** (온프레미스), REST API v2 — 4장 검증 절차 필수 |
| 인스턴스 수 | 2~3개 / 화이트리스트 프로젝트 ~50개 |
| 데이터 규모 | 10만 ~ 100만 이슈 |
| 수집 범위 | 이슈 필드 + changelog (댓글·워크로그 제외) |
| 원본 보관 | 이슈 + changelog 전부 gzip BLOB 보관 |
| 동기화 | 1~수시간 주기 증분 배치 (cron + CLI) |
| 시계열 | 이벤트 추이 + 과거 시점 상태 재현 **둘 다** |
| 교차 분석 | 같은 인스턴스 내 자동 / 인스턴스 간은 이름+타입 일치 자동 추천 후 사용자 승인 |
| 값 레벨 매핑 | 테이블만 만들고 1단계에서는 비워둠 |
| Oracle | **19c 확정.** 전용 스키마, DDL 자유 (2.4절 참고) |
| 사용자/권한 | 없음 (사내 공개) |
| 언어/라이브러리 | Python 3.12, `oracledb` (thin 모드) |
| 개발 환경 | 사외. **Oracle과 Jira 모두 없다.** DDL은 사내에서 사람이 실행하고, 코드는 테이블이 존재한다고 가정한다 |
| 반입 경로 | 사내 Git **단방향**. 의존성은 오프라인 wheel 번들 동봉 |
| DB 객체 명명 | 전부 **`TEST_` 접두사** — 일괄 삭제 후 재생성 (2.3절) |

### 1.2 저장 구조: 하이브리드

- **고정 컬럼** — 필터·정렬에 항상 쓰이는 시스템 필드는 `TEST_JIRA_ISSUE`의 실제 컬럼
- **EAV** — 프로젝트마다 다른 커스텀 필드 + 다중값 필드
- **원본 JSON** — 별도 테이블에 gzip BLOB (조회 경로 아님)
- **구간 테이블(SCD Type-2)** — changelog에서 파생. 일별 스냅샷을 물리적으로 쌓지 않고 과거 시점 재현

순수 EAV 대비 이점:

- 필터 개수만큼 self-join이 늘지 않는다
- **옵티마이저 통계가 정확해진다.** 단일 EAV 테이블에는 `status`(고유값 10개)와
  `summary`(고유값 100만개)가 한 컬럼에 섞여 있어 카디널리티 추정이 깨지고, 필터가 3개를
  넘어가면 실행계획이 불안정해진다
- drill-down 목록의 정렬·페이징이 인덱스로 끝난다

추가 비용은 `TEST_JIRA_FIELD.storage_kind` 컬럼 하나와 쿼리 빌더의 분기 한 군데뿐이다.

## 2. 전역 규약

이 규약들은 스키마 전체에 일관되게 적용된다.

### 2.1 시각은 전부 UTC로 저장한다

Jira는 ISO8601 오프셋이 붙은 시각을 준다. 인스턴스 간 서버 타임존이 다를 수 있으므로
**적재 시점에 전부 UTC로 변환**해 `TIMESTAMP` 컬럼에 넣는다. `DEFAULT`도
`SYS_EXTRACT_UTC(SYSTIMESTAMP)`를 쓴다 — `SYSTIMESTAMP`를 그냥 쓰면 DB 세션 타임존에 따라
값이 흔들린다.

**표시 타임존은 쿼리 시점에 적용한다.** 날짜 버킷팅만 변환하고, 범위 필터는 UTC 원본 컬럼에
그대로 건다:

```sql
-- GROUP BY 버킷: 표시 타임존으로 변환 (설정값, 기본 'Asia/Seoul')
TRUNC(CAST(FROM_TZ(i.created_at, 'UTC') AT TIME ZONE :tz AS DATE), 'MM')

-- 범위 필터: 경계값을 Python에서 UTC로 변환해 바인드 → 인덱스 그대로 사용
AND i.created_at >= :from_utc AND i.created_at < :to_utc
```

버킷에만 함수를 쓰고 필터에는 쓰지 않는 이 분리가 중요하다. 필터에 함수를 씌우면
`test_ix_issue_proj_created` 인덱스를 못 탄다.

### 2.2 문자열 길이

- `VARCHAR2`는 전부 **`BYTE` 세만틱을 명시**한다. 캐릭터셋이 `AL32UTF8`이고 `CHAR` 세만틱을
  쓰면 `VARCHAR2(4000 CHAR)`가 최대 16000바이트가 되어 인덱스 키 길이 제한(8K 블록 기준 약
  6400바이트)을 넘길 수 있다.
- 차원(축)으로 쓰이는 값 컬럼은 **`VARCHAR2(1000 BYTE)`로 자른다.** 옵션명·사용자명·라벨·버전명은
  전부 255자 미만이고, 1000바이트를 넘는 장문 텍스트는 애초에 축으로 쓸 수 없다. 원본은
  `TEST_ISSUE_RAW`에 그대로 있으므로 손실이 아니다. 이 제한 덕분에 인덱스 키 길이 문제가 사라진다.

### 2.3 식별자 명명 — 모든 객체에 `TEST_` 접두사

**테이블·인덱스·제약조건·시퀀스·뷰 전부 `TEST_`로 시작한다.** 예외 없다.

```
TEST_JIRA_ISSUE              테이블
TEST_IX_ISSUE_PROJ_CREATED   인덱스
TEST_PK_JIRA_ISSUE           제약조건
TEST_SEQ_ISSUE_ID            시퀀스
TEST_V_UNIFY_CANDIDATE       뷰
```

목적은 **일괄 삭제 후 재생성**이다. 스키마를 공유하는 다른 객체를 건드릴 위험 없이
`TEST_`로 시작하는 것만 골라 지울 수 있다. 설계가 아직 굳지 않은 단계라 스키마를 통째로
갈아엎는 일이 자주 생기는데, 접두사가 없으면 그때마다 무엇을 지워야 하는지 목록을 손으로
관리해야 한다.

접두사는 **하드코딩**한다. 템플릿 치환 같은 장치를 두지 않는다 — DDL 파일을 그대로 읽어
붙여넣을 수 있는 편이 지금 단계에서는 더 낫다.

나머지 규약:

- 서로게이트 PK는 `GENERATED BY DEFAULT ON NULL AS IDENTITY` (예외: `TEST_JIRA_ISSUE.issue_id`, 3.3.0절)
- 제약조건은 전부 이름을 붙인다 — 오류 메시지에 `SYS_C0012345` 대신 의미가 나온다
- 인덱스 `TEST_IX_`, 제약 `TEST_PK_`/`TEST_UQ_`/`TEST_FK_`/`TEST_CK_`
- 컬럼명에는 접두사를 붙이지 않는다

#### 일괄 삭제 스크립트

`db/ddl/drop_all.sql`. 데이터 딕셔너리에서 `TEST_` 객체만 찾아 지우므로, 테이블이 늘어도
스크립트를 고칠 필요가 없다.

```sql
BEGIN
  -- 1) 테이블 (FK 무시하고 순서 상관없이)
  FOR r IN (SELECT table_name FROM user_tables WHERE table_name LIKE 'TEST\_%' ESCAPE '\')
  LOOP
    EXECUTE IMMEDIATE 'DROP TABLE "' || r.table_name || '" CASCADE CONSTRAINTS PURGE';
  END LOOP;

  -- 2) 뷰
  FOR r IN (SELECT view_name FROM user_views WHERE view_name LIKE 'TEST\_%' ESCAPE '\')
  LOOP
    EXECUTE IMMEDIATE 'DROP VIEW "' || r.view_name || '"';
  END LOOP;

  -- 3) 시퀀스
  FOR r IN (SELECT sequence_name FROM user_sequences
            WHERE sequence_name LIKE 'TEST\_%' ESCAPE '\')
  LOOP
    EXECUTE IMMEDIATE 'DROP SEQUENCE "' || r.sequence_name || '"';
  END LOOP;
END;
/
```

세 가지가 의도적이다.

- **`LIKE 'TEST\_%' ESCAPE '\'`** — 이스케이프 없이 `'TEST_%'`로 쓰면 `_`가 와일드카드라
  `TESTX...` 같은 남의 테이블까지 지운다. 삭제 스크립트에서 이 실수는 되돌릴 수 없다
- **`CASCADE CONSTRAINTS`** — FK 때문에 삭제 순서를 신경 쓰지 않아도 된다
- **`PURGE`** — 휴지통에 남기지 않는다. 남기면 `BIN$...` 객체가 쌓이고 테이블스페이스도 안 준다

**이 스크립트는 사람이 SQL 클라이언트에서 실행한다.** CLI 명령으로 감싸지 않는다 —
되돌릴 수 없는 작업이고, 사외에 DB가 없어 스크립트 자체를 테스트할 수 없기 때문이다.
사내에서 처음 돌릴 때는 **삭제 대상을 먼저 조회해 눈으로 확인한다** (11.8절).

### 2.4 Oracle 19c 전제

**대상 버전은 19c로 확정**이며, 이 문서의 모든 DDL과 쿼리는 19c 기본 설치(Enterprise Edition
추가 옵션 없음)에서 동작한다.

#### 사용하는 기능 — 전부 19c 기본 지원

| 기능 | 도입 | 쓰이는 곳 |
|---|---|---|
| `GENERATED ... AS IDENTITY` | 12c | 모든 서로게이트 PK |
| `FETCH FIRST n ROWS ONLY` | 12c | 차트 `limit` |
| SECUREFILE LOB | 11g (19c 기본값) | `TEST_ISSUE_RAW`, `TEST_CHANGELOG_RAW` |
| `SYS_EXTRACT_UTC` / `FROM_TZ` / `AT TIME ZONE` | 9i | 2.1절 타임존 처리 |
| `TRUNC(date, fmt)` / `CONNECT BY LEVEL` | — | 날짜 버킷, `asof` 날짜 CTE |
| 단순 B-tree 인덱스 | — | 전부 |

**함수 기반 인덱스, 가상 컬럼, 파티셔닝, JSON 인덱스를 쓰지 않는다.** 인덱스는 전부 단순
B-tree라 19c에서 특별한 설정이나 옵션 라이선스가 필요 없다.

#### 19c에 없어서 쓰지 않는 것

- **네이티브 `JSON` 데이터 타입** (21c+) → 원본은 `gzip` BLOB으로 보관하고 조회 경로에서 제외
- **JSON Relational Duality View** (23ai)
- **JSON 다중값 인덱스** (21c+)

19c에도 `CREATE SEARCH INDEX ... FOR JSON`이 있지만 Oracle Text 기반이고, 애초에 원본 JSON을
조회 경로로 쓰지 않는 설계이므로 검토 대상이 아니다.

#### 19c에서 되지만 일부러 쓰지 않는 것

| 기능 | 이유 |
|---|---|
| Advanced Compression (LOB 압축) | **별도 라이선스.** Python에서 gzip으로 대체 (3~5배) |
| Partitioning | **별도 라이선스** + 현재 규모(10만~100만 이슈)에서 불필요. 12장 참고 |
| In-Memory Column Store | 별도 라이선스. 인덱스만으로 목표 성능 도달 가능 |

#### 배포 전 확인할 두 가지

```sql
-- 1) VARCHAR2 최대 길이 정책. STANDARD(기본)면 4000바이트가 상한이다.
SELECT value FROM v$parameter WHERE name = 'max_string_size';

-- 2) 타임존 파일에 Asia/Seoul이 있는지 (2.1절의 AT TIME ZONE이 여기 의존한다)
SELECT tzname FROM v$timezone_names WHERE tzname = 'Asia/Seoul';
```

`max_string_size`는 **`STANDARD`(기본값)를 전제로 설계했다.** 문서의 `VARCHAR2(4000 BYTE)`
컬럼(`from_str`, `to_str`, `error_msg`)이 정확히 이 상한값이다. `EXTENDED`로 바꾸면 32767까지
늘릴 수 있지만 **되돌릴 수 없고** DB 재시작이 필요하므로, 이 프로젝트를 위해 바꾸지 않는다.
4000바이트를 넘는 changelog 값은 절단해 저장하고 원본은 `TEST_CHANGELOG_RAW`에서 확인한다.

## 3. DB 스키마

**총 16개 테이블 + 뷰 1개 + 시퀀스 1개.** 모든 객체 이름은 `TEST_`로 시작한다 (2.3절). DDL은 `jira_dashboard/db/ddl/` 아래에 아래 절
순서대로 나눠 둔다 — **참조 순서가 곧 생성 순서다.** 특히 `test_unified_value_member`는
`test_unified_field_member`와 `test_unified_value`를 복합 FK로 참조하므로 순서를 바꾸면 생성이 실패한다.

### 3.1 메타데이터 / 카탈로그

#### TEST_JIRA_INSTANCE

N개의 Jira 도메인. **토큰은 DB에 저장하지 않는다** — `secret_ref`에는 환경변수 키 이름만 넣는다.

```sql
CREATE TABLE test_jira_instance (
  instance_id   NUMBER(10)          GENERATED BY DEFAULT ON NULL AS IDENTITY,
  instance_key  VARCHAR2(50 BYTE)   NOT NULL,
  base_url      VARCHAR2(500 BYTE)  NOT NULL,
  auth_type     VARCHAR2(10 BYTE)   DEFAULT 'PAT' NOT NULL,
  secret_ref    VARCHAR2(200 BYTE)  NOT NULL,
  is_active     CHAR(1 BYTE)        DEFAULT 'Y' NOT NULL,
  created_at    TIMESTAMP           DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP) NOT NULL,
  updated_at    TIMESTAMP           DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP) NOT NULL,
  CONSTRAINT test_pk_jira_instance      PRIMARY KEY (instance_id),
  CONSTRAINT test_uq_jira_instance_key  UNIQUE (instance_key),
  CONSTRAINT test_ck_jira_instance_auth CHECK (auth_type IN ('PAT','BASIC')),
  CONSTRAINT test_ck_jira_instance_act  CHECK (is_active IN ('Y','N'))
);
```

#### TEST_JIRA_PROJECT

`is_enabled`가 화이트리스트 플래그다. **기본값이 `'N'`인 것이 중요하다** — 카탈로그 동기화가
Jira의 전체 프로젝트를 발견해 등록하되, 명시적으로 켜기 전까지는 수집하지 않는다.

```sql
CREATE TABLE test_jira_project (
  project_id       NUMBER(10)         GENERATED BY DEFAULT ON NULL AS IDENTITY,
  instance_id      NUMBER(10)         NOT NULL,
  jira_project_id  VARCHAR2(50 BYTE)  NOT NULL,
  project_key      VARCHAR2(50 BYTE)  NOT NULL,
  name             VARCHAR2(255 BYTE),
  is_enabled       CHAR(1 BYTE)       DEFAULT 'N' NOT NULL,
  created_at       TIMESTAMP          DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP) NOT NULL,
  updated_at       TIMESTAMP          DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP) NOT NULL,
  CONSTRAINT test_pk_jira_project      PRIMARY KEY (project_id),
  CONSTRAINT test_uq_jira_project      UNIQUE (instance_id, jira_project_id),
  CONSTRAINT test_fk_jira_project_inst FOREIGN KEY (instance_id)
                                  REFERENCES test_jira_instance (instance_id),
  CONSTRAINT test_ck_jira_project_en   CHECK (is_enabled IN ('Y','N'))
);

CREATE INDEX test_ix_jira_project_key ON test_jira_project (instance_id, project_key);
```

#### TEST_JIRA_FIELD ★

**시스템의 중심 테이블이다.** 파이프라인이 `/rest/api/2/field`를 읽어 자동 갱신하고,
쿼리 API는 이 테이블만 보고 SQL을 만든다. 새 커스텀 필드가 Jira에 생겨도 DDL 변경이 없다.

```sql
CREATE TABLE test_jira_field (
  field_pk      NUMBER(10)          GENERATED BY DEFAULT ON NULL AS IDENTITY,
  instance_id   NUMBER(10)          NOT NULL,
  field_id      VARCHAR2(100 BYTE)  NOT NULL,   -- 'customfield_10001' | 'status'
  field_name    VARCHAR2(255 BYTE)  NOT NULL,
  is_custom     CHAR(1 BYTE)        NOT NULL,
  schema_type   VARCHAR2(50 BYTE),              -- Jira schema.type
  schema_items  VARCHAR2(50 BYTE),              -- array일 때 원소 타입
  custom_type   VARCHAR2(200 BYTE),             -- 커스텀 필드 플러그인 키
  value_kind    VARCHAR2(10 BYTE)   NOT NULL,   -- NUM | STR | DATE | MULTI
  storage_kind  VARCHAR2(10 BYTE)   DEFAULT 'EAV' NOT NULL,
  column_name   VARCHAR2(30 BYTE),              -- COLUMN일 때 그룹핑에 쓸 컬럼
  label_column_name VARCHAR2(30 BYTE),          -- 표시용 컬럼 (없으면 column_name 그대로)
  is_dimension  CHAR(1 BYTE)        DEFAULT 'Y' NOT NULL,
  is_measure    CHAR(1 BYTE)        DEFAULT 'N' NOT NULL,
  first_seen_at TIMESTAMP           DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP) NOT NULL,
  last_seen_at  TIMESTAMP           DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP) NOT NULL,
  CONSTRAINT test_pk_jira_field       PRIMARY KEY (field_pk),
  CONSTRAINT test_uq_jira_field       UNIQUE (instance_id, field_id),
  CONSTRAINT test_fk_jira_field_inst  FOREIGN KEY (instance_id)
                                 REFERENCES test_jira_instance (instance_id),
```

**`label_column_name`은 사용자 필드(assignee·reporter) 때문에 있다.** 표시 이름으로
그룹핑하면 **동명이인이 한 사람으로 합쳐진다** — 사내 Jira에서 충분히 흔하고, 합쳐진 뒤에는

`assignee_display_name`으로 한다. 이 컬럼이 NULL이면 `column_name`을 그대로 표시에도 쓴다.

동일한 문제가 EAV 쪽에도 있다(옵션 이름이 바뀌면 과거·현재가 다른 카테고리가 된다). 다만

**1단계에서는 테이블만 만들고 비워둔다.** 쿼리 빌더가 `LEFT JOIN + COALESCE`로 참조하므로,

**PK가 `(field_pk, raw_value)`인 이유** — 쿼리 빌더의 조인 키와 정확히 일치하고,
"한 원본 값은 최대 하나의 표준값으로만 매핑된다"를 강제한다.

**`unified_field_id`를 멤버 테이블에 중복 저장하고 복합 FK를 거는 이유** — 이게 없으면
"통합 필드 A의 표준값에, 통합 필드 B에 속한 필드의 원본 값을 매핑하는" 조합이 DB 차원에서
막히지 않는다. 그런 행이 하나만 들어가도 교차 차트의 숫자가 조용히 틀린다. 두 복합 FK가
**표준값과 원본 필드가 같은 통합 필드에 속함**을 강제한다.

값 매핑은 1단계에서 비워두는 영역이라 나중에 손댈 때 맥락이 없는 상태로 INSERT하게 된다.
그때 실수를 DB가 막아주는 것이 이 설계의 목적이다.

#### TEST_V_UNIFY_CANDIDATE (자동 추천 뷰)

자동 추천에 별도 테이블은 필요 없다. 아직 매핑되지 않은 커스텀 필드 중 이름+타입이 같고
인스턴스가 다른 쌍을 찾는 뷰 하나면 된다.

```sql
CREATE OR REPLACE VIEW test_v_unify_candidate AS
SELECT a.field_pk    AS field_pk_a,
       a.instance_id AS instance_id_a,
       b.field_pk    AS field_pk_b,
       b.instance_id AS instance_id_b,
       a.field_name,
       a.value_kind
FROM   test_jira_field a
JOIN   test_jira_field b
       ON  b.field_name  = a.field_name
       AND b.value_kind  = a.value_kind
       AND b.instance_id > a.instance_id          -- 쌍을 한 방향으로만
WHERE  a.is_custom = 'Y'
AND    b.is_custom = 'Y'
AND    NOT EXISTS (SELECT 1 FROM test_unified_field_member m WHERE m.field_pk = a.field_pk)
AND    NOT EXISTS (SELECT 1 FROM test_unified_field_member m WHERE m.field_pk = b.field_pk);
```

##### 3.3.0 `issue_id`만 IDENTITY가 아닌 이유

**Oracle의 `MERGE`는 `RETURNING`을 지원하지 않는다.** 그런데 적재 파이프라인은 이슈 한 건을
넣은 직후 그 `issue_id`를 알아야 한다 — `TEST_ISSUE_FIELD_VALUE`, `TEST_ISSUE_CHANGELOG`,
`TEST_ISSUE_RAW` 세 자식 테이블이 전부 이 값을 FK로 참조하기 때문이다.

IDENTITY를 쓰면 "MERGE 후 다시 SELECT해서 issue_id를 읽는" 왕복이 페이지마다 추가된다.
대신 **시퀀스에서 필요한 개수를 미리 받아 Python이 직접 할당**하면 왕복이 사라지고 MERGE
한 번으로 끝난다:

```sql
-- 신규 이슈 n건에 쓸 id를 한 번에 확보
SELECT test_seq_issue_id.NEXTVAL FROM dual CONNECT BY LEVEL <= :n;
```

`CACHE 1000`이라 이 호출 자체도 대부분 메모리에서 끝난다. 시퀀스 값에 구멍이 생기지만
서로게이트 키이므로 무관하다.

나머지 테이블(`test_jira_instance`, `test_jira_project`, `test_jira_field`, `unified_*`, `test_sync_run`)은
삽입 빈도가 낮고 자식이 대량 삽입되지 않으므로 IDENTITY를 그대로 쓴다.

##### 3.3.4 `deleted_at` / `delete_reason` — 삭제와 이동의 구분

이슈가 목록에서 사라지는 원인은 둘이고, 대응이 다르다.

| `delete_reason` | 원인 | 되살아날 수 있나 |
|---|---|---|
| `DELETED` | Jira에서 실제로 삭제됨 | 아니오 |
| `MOVED_OUT` | 화이트리스트 **밖** 프로젝트로 이동됨 | 예 — 그 프로젝트를 화이트리스트에 추가하면 |

둘을 구분하지 않으면 "화이트리스트를 넓혔는데 옛 이슈가 안 돌아오는" 문제가 생긴다.
판별 방법은 5.6절에 있다.

**화이트리스트 안의 다른 프로젝트로 이동한 경우는 여기 해당하지 않는다.** 이동 시 Jira가
`updated`를 갱신하므로 대상 프로젝트의 증분 수집에 자연히 잡히고, `jira_issue_id` 기준
MERGE라 같은 행의 `project_id`·`issue_key`가 갱신된다. Jira는 이슈 키를 재사용하지 않으므로
`test_uq_jira_issue_key` 충돌도 없다.

##### 3.3.1 `status_category` — 인스턴스 간 교차의 열쇠

Jira는 모든 상태를 세 카테고리 중 하나로 분류하고, 이 분류는 **인스턴스가 달라도 동일**하다.
사이트 A의 상태가 `완료`이고 B가 `Done`이어도 카테고리로 묶이므로, **값 레벨 매핑 없이도
가장 중요한 교차 분석이 성립한다.** 값 매핑을 1단계에서 비워두기로 한 결정이 안전한 이유가 이것이다.

**카테고리의 `name`이 아니라 `key`를 저장한다.** `name`(`To Do` / `In Progress` / `Done`)은
Jira 언어 설정에 따라 현지화되지만 `key`는 고정이다:

| 저장값 (key) | 영문 name | 의미 |
|---|---|---|
| `new` | To Do | 미착수 |
| `indeterminate` | In Progress | 진행 중 |
| `done` | Done | 완료 |
| `undefined` | No Category | 카테고리 미지정 |

표시용 라벨은 API 응답 계층에서 붙인다.

##### 3.3.2 `first_done_at` — `resolved_at`의 함정 회피

많은 워크플로가 상태만 `Done`으로 보내고 **Resolution을 설정하지 않는다.** 그러면
`status_category = 'done'`인데 `resolved_at`(Jira `resolutiondate`)은 NULL로 남고, 여기에
기대어 리드타임을 계산하면 조용히 틀린 숫자가 나온다.

`TEST_ISSUE_FIELD_HISTORY`에서 status가 `done` 카테고리로 **처음 진입한 시각**을 파생 계산해
저장한다. `resolved_at`보다 신뢰할 수 있고, 리드타임 차트가 조인 없이 나온다.

##### 3.3.3 Time Tracking 3컬럼

Time Tracking은 Jira 인스턴스 **전역 설정**이라, 꺼져 있으면 세 컬럼이 전부 NULL이다.
그래도 컬럼은 유지한다 — Oracle에서 NULL 컬럼의 저장 비용은 사실상 0이고, 반대로 EAV로 내리면
값이 **있는** 인스턴스에서 조인이 늘어난다. 실제 사용 여부는 `profile_fields`가 판단한다.

개별 워크로그 항목은 수집하지 않지만 `time_spent_sec`는 이슈 필드에 합계로 들어 있으므로,
**이슈별·프로젝트별 총 공수 집계는 여전히 가능하다.**

#### TEST_ISSUE_FIELD_VALUE

```sql
CREATE TABLE test_issue_field_value (
  issue_id NUMBER(12)          NOT NULL,
  field_pk NUMBER(10)          NOT NULL,
  val_seq  NUMBER(4)           DEFAULT 0 NOT NULL,   -- 다중값 필드의 순번
  val_str  VARCHAR2(1000 BYTE),
  val_num  NUMBER,
  val_date TIMESTAMP,                                 -- UTC
  val_id   VARCHAR2(100 BYTE),                        -- 옵션/사용자의 원본 ID
  CONSTRAINT test_pk_ifv       PRIMARY KEY (issue_id, field_pk, val_seq),
  CONSTRAINT test_fk_ifv_issue FOREIGN KEY (issue_id) REFERENCES test_jira_issue (issue_id),
  CONSTRAINT test_fk_ifv_field FOREIGN KEY (field_pk) REFERENCES test_jira_field (field_pk)
);

CREATE INDEX test_ix_ifv_str ON test_issue_field_value (field_pk, val_str, issue_id);
```

- `val_seq` — `labels`, `components`, `fixVersions`, 멀티셀렉트를 행 여러 개로 저장
- `val_id` — 옵션·사용자의 **원본 ID**. Jira에서 옵션 이름을 바꿔도 과거 데이터를 추적할 수 있다

**인덱스는 `test_ix_ifv_str` 하나만 먼저 만든다.** Oracle 복합 인덱스는 선행 컬럼(`field_pk`)이
NOT NULL이면 모든 행을 색인하므로, `val_num`/`val_date` 인덱스를 미리 만들면 대부분 NULL인
30M 행을 통째로 색인해 공간과 쓰기 비용만 든다. 숫자·날짜 커스텀 필드가 실제로 축으로
쓰이는 것이 `profile_fields`로 확인된 뒤에 추가한다:

```sql
  author_display_name VARCHAR2(255 BYTE),
  changed_at          TIMESTAMP           NOT NULL,   -- UTC

```

`test_uq_changelog`가 재적재 멱등성을 보장한다. 키에 `item_seq`를 넣은 이유는 하나의 history
엔트리가 같은 필드에 대해 여러 item을 담는 경우가 있기 때문이다 — `field_name`만으로 묶으면
그때 UNIQUE 위반으로 배치가 죽는다.

`field_pk`가 nullable인 것은 의도적이다. changelog에는 카탈로그에 없는 가상 필드
(`Link`, `Attachment`, `Workflow` 등)가 등장한다. 이들은 원본 `field_name`으로만 보존한다.

#### TEST_ISSUE_FIELD_HISTORY ★

changelog에서 파생하는 **구간(SCD Type-2) 테이블**이다.

```sql
CREATE TABLE test_issue_field_history (
  issue_id   NUMBER(12)          NOT NULL,
  field_pk   NUMBER(10)          NOT NULL,
  valid_from TIMESTAMP           NOT NULL,   -- UTC, 경계 포함
  valid_to   TIMESTAMP           DEFAULT TIMESTAMP '9999-12-31 00:00:00' NOT NULL,
  val_str    VARCHAR2(1000 BYTE),
  val_id     VARCHAR2(100 BYTE),
  CONSTRAINT test_pk_ifh       PRIMARY KEY (issue_id, field_pk, valid_from),
  CONSTRAINT test_fk_ifh_issue FOREIGN KEY (issue_id) REFERENCES test_jira_issue (issue_id),
  CONSTRAINT test_fk_ifh_field FOREIGN KEY (field_pk) REFERENCES test_jira_field (field_pk),
  CONSTRAINT test_ck_ifh_range CHECK (valid_from < valid_to)
);

CREATE INDEX test_ix_ifh_scan ON test_issue_field_history
  (field_pk, valid_from, valid_to, issue_id);
```

설계 판단 세 가지:

- **마지막 구간의 `valid_to`는 NULL이 아니라 `9999-12-31`이다.** NULL이면
  `valid_from <= d AND (valid_to IS NULL OR d < valid_to)` 같은 OR 조건이 되어 인덱스 범위
  스캔이 깨진다. 센티넬 값을 쓰면 조건이 단순 범위로 남는다.
- **일별 스냅샷을 물리적으로 쌓지 않는다.** 100만 이슈 × 365일 = 3.6억 행이 되지만, 구간
  테이블은 이슈당 전이 횟수만큼(수천만 행 이하)이다.
- **추적 대상은 `is_dimension='Y'`인 필드로 제한한다.** summary·description 변경 이력까지
  구간화하면 테이블만 부풀고 쓰이지 않는다.

```sql
LOB (payload) STORE AS SECUREFILE (DISABLE STORAGE IN ROW);

CREATE TABLE test_changelog_raw (
  issue_id     NUMBER(12)        NOT NULL,

  fetched_at   TIMESTAMP DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP) NOT NULL,

LOB (payload) STORE AS SECUREFILE (DISABLE STORAGE IN ROW);
```

- **압축은 Python에서 gzip으로 한다.** Oracle Advanced Compression은 별도 라이선스다.
  예상 용량은 원본 15~30GB → 압축 후 3~6GB.
- `DISABLE STORAGE IN ROW`로 LOB을 테이블 세그먼트 밖에 둔다. 이러면 `TEST_ISSUE_RAW`를
  스캔할 일이 있어도 BLOB이 딸려오지 않는다.
- **`payload_hash`는 보관 부산물이 아니라 성능 기능이다.** Jira의 `updated`가 갱신됐어도
  우리가 보는 필드는 안 바뀐 경우가 흔한데(코멘트 추가, 워치 변경 등), 해시로 걸러
  EAV·이력 재기록을 통째로 건너뛴다.

## 4. Jira API 계약과 시스템 필드 매핑

### 4.0 Jira DC 10.3 — 코드 작성 전 반드시 검증할 것

**이 문서의 Jira API 서술은 전부 "검증 대상 가정"이다.** 사내 인스턴스가 **Data Center 10.3**
이므로, 9.x 기준 지식이나 Cloud 문서를 그대로 적용하면 안 된다.

#### 공개 문서로 확인된 것 (2026-08 기준)

| 사실 | 우리에게 주는 의미 |
|---|---|
| `/rest/api/2/search` 제거는 **Jira Cloud** 이야기다. Cloud는 `/rest/api/3/search/jql`로 이전했다 | **DC는 해당 없다.** 검색하다 이 문서를 만나면 Cloud용인지 먼저 확인할 것 |
| "Jira DC 10.4의 새 search API" 공지는 **REST가 아니라 앱 벤더용 Java/Lucene 인덱스 API**다 | 우리와 무관하다. 이름 때문에 겁먹기 쉬운 지점 |
| Jira **10.0**에서 "이전에 deprecated되었던 REST 엔드포인트 제거"가 있었다. 구체 목록은 공개 changelog에서 확인되지 않음 | **사내 인스턴스에서 직접 확인해야 한다** |
| Jira DC용 **공식 OpenAPI/Swagger 스펙은 없다.** WADL만 제공된다 | 스펙 파일을 받아 코드를 생성하는 방식은 불가. 실호출 검증이 유일한 확실한 방법 |
| Jira **11**에서 search 관련 deprecation이 예고되어 있다 | 지금 10.3이라 무관하지만, 업그레이드 시 재검토 항목으로 기록 |

#### 작업 순서 규칙

**`jira/client.py`와 `jira/parser.py`를 쓰기 전에 위 표를 확인하고 결과를
`docs/api-verification.md`에 기록한다.** 항목마다 확인 방법·실제 응답 발췌·판정을 남긴다.
확인 전에 쓴 코드는 추측이며, 사외에서는 그 추측이 맞는지 알 방법이 없다.

사외 작업 중에는 이 표가 **미확인 상태로 남는다.** 그래서 `FakeJiraClient`의 픽스처는
"검증된 사실"이 아니라 "표의 가정을 그대로 구현한 것"이며, 11.7절의 사내 첫날 절차에서
`doctor`가 가정을 깨면 픽스처와 코드를 함께 고친다.

### 4.1 시스템 필드 매핑

`sync_catalog`가 `TEST_JIRA_FIELD`를 채울 때 이 표를 참조해 `storage_kind`를 결정한다.
**표에 없는 모든 필드는 자동으로 `EAV`가 된다.**

| Jira `field_id` | `column_name` (그룹핑) | `label_column_name` (표시) | `value_kind` | dim | msr |
|---|---|---|---|---|---|
| `issuetype` | `issue_type_name` | — | STR | Y | N |
| `status` | `status_name` | — | STR | Y | N |
| `status_category` ※ | `status_category` | — | STR | Y | N |
| `priority` | `priority_name` | — | STR | Y | N |
| `resolution` | `resolution_name` | — | STR | Y | N |
| `assignee` | `assignee_user_key` | `assignee_display_name` | STR | Y | N |
| `reporter` | `reporter_user_key` | `reporter_display_name` | STR | Y | N |
| `parent` | `parent_key` | — | STR | Y | N |
| `summary` | `summary` | — | STR | **N** | N |
| `created` | `created_at` | — | DATE | Y | N |
| `updated` | `updated_at` | — | DATE | Y | N |
| `resolutiondate` | `resolved_at` | — | DATE | Y | N |
| `duedate` | `due_date` | — | DATE | Y | N |
| `first_done_at` ※ | `first_done_at` | — | DATE | Y | N |
| `timeoriginalestimate` | `original_estimate_sec` | — | NUM | N | Y |
| `timeestimate` | `remaining_estimate_sec` | — | NUM | N | Y |
| `timespent` | `time_spent_sec` | — | NUM | N | Y |

**※ 표시 두 개는 Jira `/rest/api/2/field`에 존재하지 않는 합성 필드다.** `sync_catalog`가
인스턴스마다 직접 생성해 넣어야 한다 (`is_custom='N'`). 이렇게 등록해두면 쿼리 API가
`{"kind":"system","field_id":"status_category"}`로 다른 필드와 똑같이 참조할 수 있다.

`summary`는 `is_dimension='N'`이다. 고유값이 이슈 수와 같아 축으로 쓰면 의미가 없다.

**`labels`, `components`, `fixVersions`는 시스템 필드지만 표에 없다 — 의도적으로 EAV로
보낸다.** 다중값이라 고정 컬럼에 담을 수 없고, EAV의 `val_seq`가 정확히 이 용도다.

### 4.2 카탈로그 코너케이스

**동명 커스텀 필드** — Jira는 같은 이름의 커스텀 필드를 여러 개 만드는 것을 막지 않는다.
한 인스턴스에 `결함원인`이 두 개 있을 수 있고, 이때 두 곳이 영향을 받는다.

- `TEST_V_UNIFY_CANDIDATE`가 상대 인스턴스의 같은 이름 필드와 **여러 쌍**을 제안한다.
  뷰는 후보만 제시하고 확정은 사람이 하므로 치명적이지 않지만, UI가 `field_id`를 함께
  보여줘야 사용자가 고를 수 있다
- changelog 매칭이 모호해진다 (아래)

**changelog 항목 → `field_pk` 매칭** — Jira DC changelog의 item은 필드 **ID가 아니라 이름**을
담는 것이 원칙이고, 8.4 이후 버전은 `fieldId`를 함께 준다. 매칭 순서:

1. `fieldId`가 있으면 → `test_jira_field.field_id`로 정확히 매칭
2. 없으면 → `test_jira_field.field_name`으로 매칭. **동명 필드가 둘 이상이면 모호하므로
   `field_pk`를 NULL로 두고 `field_name`만 보존한다** (임의로 하나를 고르면 이력이 조용히
   섞인다)
3. 어느 쪽도 못 찾으면 NULL (`Link`, `Attachment`, `Workflow` 같은 가상 필드)

`field_pk`가 NULL인 changelog 행은 `derive_history`에서 건너뛴다. 구간 테이블은
`field_pk`가 NOT NULL이기 때문이다.

**필드 메타데이터 변경 감지** — `sync_catalog`는 upsert만 하지 않고 **변경을 감지해야 한다.**

| 변경 | 결과 | 대응 |
|---|---|---|
| `value_kind` 변경 (Jira에서 커스텀 필드 타입 변경) | 기존 EAV 값이 엉뚱한 컬럼에 남음 | 로그 + 해당 인스턴스 전 프로젝트 `full_resync_requested='Y'` |
| `storage_kind` 변경 (4.1절 매핑표를 우리가 수정) | EAV와 고정 컬럼에 값이 **동시에** 존재 → 이중 계상 | 해당 `field_pk`의 EAV 행 삭제 + 전체 재수집. **매핑표 수정은 DDL 변경급 사건으로 다룬다** |
| `field_name` 변경 | 통합 필드 추천만 영향 | 갱신만, 재수집 불필요 |
| Jira에서 필드 삭제 | 과거 데이터가 참조 중 | 행을 지우지 않고 `last_seen_at`만 낡게 둔다 |

**프로젝트 키 변경** — Jira는 프로젝트 키 변경을 허용한다(`PROJ` → `PRJ`). 그러면 그
프로젝트의 **모든 이슈 키가 바뀌지만 `updated`는 갱신되지 않는다.** 증분 수집에 걸리지
않으므로 DB의 `issue_key`가 영구히 낡은 채로 남는다.

→ `sync_catalog`가 `test_jira_project.project_key` 변경을 감지하면 그 프로젝트에
`full_resync_requested='Y'`를 세운다. 이건 감지하지 않으면 알아챌 방법이 없는 종류의 오류다.

### 4.3 값 파싱 규칙

`parser.py`가 Jira 값을 `(val_str, val_num, val_date, val_id)`로 변환하는 규칙:

| Jira `schema.type` | 저장 방식 | `value_kind` |
|---|---|---|
| `string` | `val_str` (1000바이트 초과 시 절단) | STR |
| `number` | `val_num` | NUM |
| `date` | `val_date` (00:00 UTC) | DATE |
| `datetime` | `val_date` (UTC 변환) | DATE |
| `option` | `val_str` = value, `val_id` = id | STR |
| `user` | `val_str` = displayName, `val_id` = key | STR |
| `priority`/`status`/`resolution`/`issuetype`/`version`/`component` | `val_str` = name, `val_id` = id | STR |
| `array` | 원소마다 행 하나, `val_seq` = 0..n | MULTI |
| 그 외 (플러그인 커스텀 타입) | JSON 문자열을 `val_str`에 절단 저장, `is_dimension='N'` | STR |

파싱 시 지켜야 할 세 가지:

- **`val_str`은 `strip()` 후 저장한다.** 라벨처럼 사용자 자유 입력인 값에 앞뒤 공백이 섞이면
  `"Blocker"`와 `" Blocker"`가 서로 다른 막대가 된다. 대소문자는 **보존한다** — Jira가
  구분하므로 우리가 합치면 원본과 어긋난다
- **값이 없는 필드는 EAV에 행을 넣지 않는다.** NULL 행을 넣으면 `TEST_JIRA_PROJECT_FIELD`의
  `issue_count`가 부풀어 빈 필드가 축 후보에 뜬다
- **`array`가 빈 배열이면 행 0개**다. NULL과 구분하지 않는다

**절단은 두 번 일어날 수 있다.** changelog의 `to_str`는 4000바이트까지 저장하지만
`TEST_ISSUE_FIELD_HISTORY.val_str`은 1000바이트이므로, 이력 파생 시 한 번 더 잘린다.
`is_dimension='Y'`인 필드의 값은 1000바이트를 넘지 않으므로 실무상 문제가 없지만,
원본 확인이 필요하면 `TEST_CHANGELOG_RAW`를 본다.

## 5. 수집 파이프라인

```
runner.py (인스턴스 단위 병렬 2~3, 인스턴스 내 프로젝트는 순차)
  ├─ 1. sync_catalog          /field, /project → TEST_JIRA_FIELD, TEST_JIRA_PROJECT upsert
  ├─ 2. sync_issues           프로젝트별 증분 수집 → TEST_JIRA_ISSUE + RAW + EAV + CHANGELOG
  ├─ 3. derive_history        변경된 이슈만 TEST_ISSUE_FIELD_HISTORY 재구성
  ├─ 4. update_first_done_at
  ├─ 5. profile_fields        TEST_JIRA_PROJECT_FIELD 갱신 (일 1회)
  └─ 6. detect_deleted        삭제/이동 이슈 감지 (일 1회)
```

### 5.0 병렬 단위는 인스턴스다 — 프로젝트가 아니다

같은 인스턴스의 프로젝트를 병렬로 돌리면 두 가지가 물린다.

- **이동 중인 이슈의 경합.** 이슈가 프로젝트 A → B로 옮겨진 직후, 워터마크 겹침 구간(5분)
  때문에 A와 B의 수집에 **같은 이슈가 동시에** 걸린다. 두 워커가 같은 `issue_id`에 대해
  EAV를 DELETE + INSERT하면 PK 위반이나 데드락이 난다
- **Jira DC 부하 집중.** 같은 서버에 8개 워커가 동시에 `fields=*all` 요청을 던진다

인스턴스가 2~3개뿐이므로 **인스턴스 단위 병렬 + 인스턴스 내 순차**로 충분하다. 증분 배치는
프로젝트당 보통 수 초이므로 50개를 순차 처리해도 주기(1~수시간) 안에 넉넉히 끝난다.

전체 재수집처럼 오래 걸리는 작업에서 프로젝트 병렬화가 필요해지면, 그때 이슈 단위 잠금
(`SELECT ... FOR UPDATE` on `TEST_JIRA_ISSUE`)을 도입한다. 지금은 넣지 않는다.

### 5.1 카탈로그 동기화

- `GET /rest/api/2/field` → `TEST_JIRA_FIELD` upsert. 4.1절 매핑표로 `storage_kind` 결정
- `GET /rest/api/2/project` → `TEST_JIRA_PROJECT` upsert. **`is_enabled`는 절대 덮어쓰지 않는다**
  (화이트리스트는 사람이 정한다)
- 합성 필드(`status_category`, `first_done_at`)를 인스턴스마다 등록
- 이번 실행에서 본 필드는 `last_seen_at` 갱신. Jira에서 삭제된 필드는 행을 지우지 않고
  남겨둔다 — 과거 데이터가 참조하고 있다

### 5.2 증분 수집 (`sync_issues.py`)

**JQL**: `project = X AND updated >= "YYYY-MM-DD HH:mm" ORDER BY updated ASC`
**호출**: `POST /rest/api/2/search` · `maxResults=100` · `fields=*all` · **`expand=changelog`**

`expand=changelog`가 성능의 열쇠다. Jira DC의 search API는 이슈당 최대 100개의 이력 항목을
인라인으로 함께 준다 — **이슈 100건과 그 이력 전체를 요청 1회로 받는다.** 이력이 100개를
넘는 소수의 이슈만 `GET /issue/{key}?expand=changelog&startAt=...`로 보충한다.
(응답의 `changelog.total > changelog.maxResults`로 판별한다.)

이슈마다 개별 호출하는 방식 대비 요청 수가 약 100분의 1이다.

#### 워터마크 경계 처리 — 조용히 데이터를 잃는 지점

`startAt` 페이징 도중 이슈가 수정되면 정렬 순서가 밀려 건너뛰기가 발생한다. 대응:

- **`ORDER BY updated ASC` 고정.** 수정된 이슈가 뒤로 밀리므로 앞쪽 페이지의 건너뛰기가 없다
- **다음 배치 시작 워터마크 = 이번 배치 최대 `updated` − 5분** (의도적 중복 구간)
- 모든 적재가 MERGE 기반 멱등이므로 중복 수집은 무해하다

#### 적재 (페이지 100건 = 트랜잭션 1개)

**`TEST_ISSUE_RAW`·`TEST_CHANGELOG_RAW`는 `TEST_JIRA_ISSUE`를 FK로 참조하므로 이슈보다 먼저 넣을 수 없다.**
따라서 "해시부터 비교하고 같으면 전부 스킵"을 하려면, 쓰기가 아니라 **읽기**를 먼저 해야 한다.

```
① 기존 상태 조회 (페이지 100건을 한 쿼리로)
   SELECT i.jira_issue_id, i.issue_id, r.payload_hash
   FROM   test_jira_issue i LEFT JOIN test_issue_raw r ON r.issue_id = i.issue_id
   WHERE  i.instance_id = :inst AND i.jira_issue_id IN (:ids...)

② 분류
   해시 동일  → UPDATE test_jira_issue SET synced_at = :now  로 끝. ③~⑥ 스킵
   해시 다름  → 기존 issue_id 재사용하여 ③으로
   신규       → test_seq_issue_id에서 필요 개수만큼 채번하여 ③으로

③ TEST_JIRA_ISSUE          MERGE (issue_id를 우리가 지정)
④ TEST_ISSUE_RAW / TEST_CHANGELOG_RAW   MERGE          ← ③ 이후여야 FK 충족
⑤ TEST_ISSUE_FIELD_VALUE   해당 issue_id DELETE 후 executemany INSERT
⑥ TEST_ISSUE_CHANGELOG     MERGE (jira_history_id + item_seq 기준)
```

`issue_id`를 시퀀스에서 미리 받아 직접 할당하기 때문에 ③이 `MERGE` 하나로 끝나고
`RETURNING` 왕복이 없다 (3.3.0절).

**EAV는 부분 갱신하지 않고 이슈 단위로 지우고 다시 넣는다.** 다중값 필드에서 "어떤 값이
빠졌는지" 계산하는 로직이 통째로 사라져 코드가 단순해지고 버그가 줄어든다. 이슈당 수십
행이므로 비용도 미미하다.

**해시 스킵 경로에서도 `synced_at`은 갱신한다.** 그래야 "이 이슈를 마지막으로 확인한 시각"이
정확해지고, 삭제 감지가 오래된 행을 구분할 수 있다.

#### changelog 보충 호출

`changelog.total > changelog.maxResults`인 이슈만
`GET /issue/{key}?expand=changelog&startAt=100`으로 나머지를 받는다.
**Jira의 changelog는 오래된 것부터 오름차순**이고 인라인 응답은 앞쪽 100개를 주므로,
보충은 `startAt=100`부터다. 이 방향 가정은 첫 구현 시 실제 응답으로 반드시 확인한다 —
반대라면 오래된 이력이 통째로 유실되고, 구간 테이블이 조용히 틀린다.

#### `fields=*all`에 대해

`*all`은 무겁지만 우리에게는 필수다 — 어떤 커스텀 필드가 있을지 미리 모르기 때문이다.
다만 **`expand`에 `renderedFields`를 넣지 않는다.** HTML 렌더링까지 붙어 응답이 배로
커지는데 우리는 쓰지 않는다.

### 5.3 이력 파생 (`derive_history.py`)

이슈 하나 안에서 완결되는 로직이다:

```
필드별로 changed_at 순 정렬
  첫 구간:   [issue.created,         첫 변경.changed_at)   값 = 첫 변경.from_str
  중간 구간: [변경N.changed_at,      변경N+1.changed_at)   값 = 변경N.to_str
  마지막:    [마지막변경.changed_at, 9999-12-31)           값 = 마지막.to_str
  변경 없음: [issue.created,         9999-12-31)           값 = 현재값
```

이번 배치에서 바뀐 `issue_id` 집합만 DELETE 후 재생성한다. 이슈 단위로 닫혀 있어
부분 실패가 다른 이슈를 오염시키지 않는다.

**대상 필드**는 `field_pk IS NOT NULL AND is_dimension='Y'`인 changelog 행뿐이다.
`field_pk`가 NULL인 행(매칭 실패·가상 필드)은 건너뛴다 — 구간 테이블의 `field_pk`가
NOT NULL이기 때문이다.

**커밋 단위는 이슈 1000건**이다. 전체 재수집 시 "바뀐 이슈"가 100만 건이 되는데, 이를
한 트랜잭션에 넣으면 UNDO가 터진다. 이슈 단위로 닫힌 로직이라 중간 커밋이 안전하다.

**경계 조건** (테스트로 반드시 고정할 것):

| 상황 | 처리 |
|---|---|
| 변경 이력이 없는 이슈 | 단일 구간 `[created, 9999-12-31)`, 값 = 현재값 |
| 같은 `changed_at`에 같은 필드 변경이 둘 이상 | 마지막 것만 남긴다. 앞의 것은 길이 0 구간이라 `test_ck_ifh_range`에 걸린다 |
| 값이 비워짐 (`to_str` NULL) | `val_str` NULL인 구간을 정상적으로 만든다 |
| `changed_at` < 이슈 `created` (데이터 이관 등) | `valid_from`을 `created`로 clamp |
| 첫 changelog의 `from_str`이 NULL | 첫 구간의 값을 NULL로 둔다. 현재값으로 채우지 않는다 — 그 값은 나중에 설정된 것이다 |
| **이력의 마지막 값 ≠ 이슈의 현재값** | 이력 유실을 의미한다. 마지막 구간을 **현재값으로 덮고** 경고 로그를 남긴다 (아래) |

마지막 항목이 중요하다. changelog가 잘렸거나(보충 호출 실패), Jira 관리자가 이력을 지웠거나,
DB 이관으로 이력 없이 값만 바뀐 경우 이력의 종점과 현재 상태가 어긋난다. **차트의 현재
시점 값이 실제와 다르게 나오는 것이 최악이므로, 현재값을 신뢰하고 이력을 맞춘다.**
경고 로그는 남겨 얼마나 흔한지 파악한다.

#### `status_category` 이력을 함께 생성한다

`status` 이력에는 인스턴스마다 다른 **상태 이름**이 들어간다(`완료` vs `Done`). 이대로면
과거 시점 차트에서 인스턴스 간 교차가 불가능하다 — 현재 시점은 `TEST_JIRA_ISSUE.status_category`
덕분에 되는데 과거만 안 되는 비대칭이 생긴다.

그래서 `status` 구간을 만들 때 **합성 필드 `status_category`의 구간을 함께 만든다.**
상태명 → 카테고리 대응은 `GET /rest/api/2/status`로 받아 인스턴스별 딕셔너리로 들고 있는다
(5.4절과 같은 자료).

**연속한 같은 카테고리 구간은 병합한다.** `개발중` → `리뷰중` → `QA` 는 셋 다
`indeterminate`이므로 구간 3개가 아니라 1개여야 한다. 병합하지 않으면 행 수가 불필요하게
늘고, `first_done_at` 계산도 지저분해진다.

이 파생 덕분에 `first_done_at`(5.4절)은 `status_category` 구간에서 `'done'`인 첫 구간의
`valid_from`을 읽는 것으로 끝난다.

### 5.4 `first_done_at` 갱신

3단계가 만든 `status_category` 구간에서 값이 `'done'`인 **첫 구간의 `valid_from`**을 뽑아
`TEST_JIRA_ISSUE`를 UPDATE한다. 한 쿼리로 끝난다.

```sql
MERGE INTO test_jira_issue t
USING (
  SELECT h.issue_id, MIN(h.valid_from) AS first_done_at
  FROM   test_issue_field_history h
  JOIN   test_jira_field f ON f.field_pk = h.field_pk AND f.field_id = 'status_category'
  WHERE  h.val_str = 'done'
  AND    h.issue_id IN (:changed_ids)
  GROUP  BY h.issue_id
) s ON (t.issue_id = s.issue_id)
WHEN MATCHED THEN UPDATE SET t.first_done_at = s.first_done_at;
```

**되돌아간 이슈**(Done → 재오픈)는 `MIN`이므로 **처음** 완료된 시각을 유지한다. 이게 맞다 —
리드타임은 "처음 끝난 시점까지"로 세는 것이 통상적이다. 재오픈 후 다시 닫힌 시각이
필요해지면 그때 별도 지표로 다룬다.

이슈가 완료 상태에서 벗어났는데 `first_done_at`이 남아 있는 것은 정상이다. "지금 완료됐나"는
`status_category`가, "언제 처음 완료됐나"는 `first_done_at`이 답한다.

### 5.5 필드 프로파일링 (일 1회)

프로젝트 × 필드마다 값이 있는 이슈 수와 고유값 수를 세어 `TEST_JIRA_PROJECT_FIELD`를 갱신한다.

**프로젝트 50개 × 필드 300개 = 15,000번의 COUNT 쿼리를 돌리면 안 된다.** 커스텀 필드는
EAV 테이블을 **한 번 훑는 GROUP BY 하나**로 전부 계산된다:

```sql
MERGE INTO test_jira_project_field t
USING (
  SELECT i.project_id,
         v.field_pk,
         COUNT(DISTINCT v.issue_id) AS issue_count,
         COUNT(DISTINCT COALESCE(v.val_str, TO_CHAR(v.val_num), TO_CHAR(v.val_date)))
                                    AS distinct_value_count
  FROM   test_issue_field_value v
  JOIN   test_jira_issue i ON i.issue_id = v.issue_id
  WHERE  i.deleted_at IS NULL
  GROUP  BY i.project_id, v.field_pk
) s
ON (t.project_id = s.project_id AND t.field_pk = s.field_pk)
WHEN MATCHED THEN UPDATE SET t.issue_count = s.issue_count,
                             t.distinct_value_count = s.distinct_value_count,
                             t.last_profiled_at = SYS_EXTRACT_UTC(SYSTIMESTAMP)
WHEN NOT MATCHED THEN INSERT (...) VALUES (...);
```

시스템 필드는 `TEST_JIRA_ISSUE`를 한 번 훑으며 컬럼별 `COUNT(col)`을 한 쿼리에 나열한다
(17개 컬럼 = 스캔 1회).

**GROUP BY 결과에 없는 (프로젝트, 필드) 조합은 `issue_count`를 0으로 리셋해야 한다.**
그러지 않으면 필드를 비운 뒤에도 옛 카운트가 남아 축 후보에 계속 뜬다. MERGE 전에 해당
프로젝트들의 행을 `issue_count = 0`으로 UPDATE하고 시작한다.

`issue_count = 0`이면 축 후보에서 제외된다. Time Tracking 3컬럼이 전부 0건이면 로그로 알린다.

### 5.6 삭제 감지 (일 1회)

증분 수집은 삭제를 원리적으로 감지할 수 없다. 프로젝트별로 `fields=id`로 전체 id 목록만
가볍게 조회해, DB에는 있는데 Jira에 없는 이슈를 후보로 뽑는다.

**`maxResults`는 요청값이 아니라 응답값을 믿는다.** Jira DC의
`jira.search.views.default.max`(기본 1000)에 따라 서버가 요청보다 작은 페이지를 줄 수 있고,
요청값만 믿고 페이징하면 조용히 건너뛴다.

**후보를 바로 삭제 처리하면 안 된다.** 이슈가 사라지는 원인이 둘이고 대응이 다르기 때문이다
(3.3.4절). 후보는 보통 소수이므로 한 건씩 확인한다:

```
GET /rest/api/2/issue/{jira_issue_id}?fields=project
  404          → deleted_at = now, delete_reason = 'DELETED'
  200, 화이트리스트 밖 프로젝트 → deleted_at = now, delete_reason = 'MOVED_OUT'
  200, 화이트리스트 안 프로젝트 → 삭제 아님. project_id·issue_key를 갱신하고 살려둔다
```

세 번째 경우는 이동 직후 양쪽 워터마크의 틈에 빠진 이슈다. 여기서 잡지 않으면
"Jira에는 있는데 대시보드에서 사라진 이슈"가 된다.

반대로 **되살리는 경로**도 필요하다. `MOVED_OUT`으로 표시된 이슈의 프로젝트가 나중에
화이트리스트에 추가되면, 그 프로젝트의 첫 수집(워터마크 없음 = 전체 수집)에서 다시 잡히므로
`deleted_at`·`delete_reason`을 NULL로 되돌린다. **적재 시 이 두 컬럼을 항상 NULL로 덮는 것을
MERGE에 넣어둔다.**

### 5.7 oracledb 사용 지침

- **thin 모드 기본** — Instant Client 설치가 필요 없다. Kerberos 등이 필요할 때만 thick 검토
- `oracledb.create_pool(min=2, max=8)` 커넥션 풀
- `cursor.executemany(..., batcherrors=True)` — 배치 적재 + 부분 실패 격리
- BLOB 적재 시 `cursor.setinputsizes(oracledb.DB_TYPE_BLOB)`
- **모든 조회는 바인드 변수** (커서 공유 + injection 차단)

### 5.8 오류 처리

| 상황 | 처리 |
|---|---|
| HTTP 429 / 503 | exponential backoff 재시도 |
| HTTP 401 / 403 | 즉시 중단, `TEST_SYNC_RUN.error_msg` 기록, 워터마크 전진 안 함 |
| 프로젝트 1개 실패 | **격리** — 다른 프로젝트는 계속. 해당 프로젝트만 워터마크 유지 |
| 파싱 실패 이슈 | 로그 + 스킵. raw는 저장돼 있어 나중에 재처리 가능 |

### 5.9 스케줄링

cron이 `python -m jira_dashboard.cli sync`를 호출한다. 상태가 전부 DB에 있어 프로세스가
죽어도 다음 주기에 자동 복구된다.

### 5.10 배치 실행 안전장치

cron 기반 배치에서 반드시 물리는 것들이다.

**중복 실행 방지 — 배치가 주기보다 오래 걸리는 경우**
1시간 주기인데 전체 재수집이 3시간 걸리면 세 프로세스가 겹친다. 겹치면 같은 이슈에 대해
EAV DELETE/INSERT가 경합한다.

DB 상태 컬럼으로 막으려 하면 안 된다 — 프로세스가 죽었을 때 락이 영원히 남는다.
**OS 락을 쓴다:**

```
*/60 * * * * flock -n /var/run/jira_sync.lock python -m jira_dashboard.cli sync
```

`flock -n`은 이미 실행 중이면 즉시 종료한다. 프로세스가 죽으면 커널이 락을 자동 해제하므로
좀비 락이 생기지 않는다.

**좀비 `RUNNING` 정리**
배치 시작 시 `TEST_SYNC_RUN`에서 `status='RUNNING'`이고 `started_at`이 6시간 이전인 행을
`FAILED`로 정리한다. `TEST_SYNC_WATERMARK.last_status`도 함께 정리한다. 이 값들은 상태 표시용일
뿐 실행 제어에 쓰지 않는다.

**신규 프로젝트의 첫 수집**
화이트리스트에 새로 켜면 `TEST_SYNC_WATERMARK` 행이 없다. 이때는 워터마크를 `NULL`로 취급해
`updated >= "1970-01-01 00:00"`으로 전체를 수집하고, 성공 후 행을 생성한다. 별도 분기가
필요 없도록 워터마크 조회를 `COALESCE(last_synced_updated_at, TIMESTAMP '1970-01-01')`로
쓴다.

**`full_resync_requested` 플래그의 수명**
| 시점 | 동작 |
|---|---|
| 세우는 곳 | `/api/sync/trigger`, `value_kind` 변경 감지, 프로젝트 키 변경 감지 (4.2절) |
| 읽는 곳 | `sync_issues` 시작 시. `'Y'`면 워터마크를 무시하고 전체 수집 |
| **내리는 곳** | 그 프로젝트의 수집이 **성공으로 끝난 직후**. 실패하면 그대로 두어 다음 배치가 다시 시도한다 |

성공 시점에 내리지 않으면 매 배치가 전체 재수집을 반복한다.

**전체 재수집 시 워터마크**
전체 수집이 끝난 뒤의 워터마크도 "이번 배치 최대 `updated` − 5분"이다. 수집 시작 시각을
쓰면 수집 도중 변경된 이슈를 놓친다.

## 6. 쿼리 API (설계만 — 이번 구현 범위 밖)

> 이 장은 **다음 단계**다. 데이터가 쌓인 뒤 착수한다.
> 다만 여기 정의된 `TEST_JIRA_FIELD.storage_kind`·`label_column_name` 사용 방식이
> 스키마 설계의 근거이므로, 파이프라인을 만들 때도 이 장의 전제를 깨지 않아야 한다.

### 6.1 필드 참조(ref) — 교차 분석의 해법

| kind | 참조 키 | 교차 범위 |
|---|---|---|
| `system` | `field_id` (`"status"`, `"created"`) | **모든 인스턴스 자동 통합** — field_id가 Jira 표준 |
| `field` | `field_pk` | 한 인스턴스 내 모든 프로젝트 자동 교차 — customfield ID는 인스턴스 전역 |
| `unified` | `unified_field_id` | 인스턴스 간 — 멤버 `field_pk` 집합으로 확장 |

**"동일 필드를 가진 프로젝트끼리는 매핑 없이 교차"** 라는 요구가 `system`과 `field`로 자동
충족된다. `unified`는 인스턴스가 다를 때만 필요하다.

### 6.2 차트 스펙

```json
{
  "projects": [12, 13, 27],
  "x":       {"ref": {"kind": "field",  "field_pk": 3301}, "bucket": null},
  "series":  {"ref": {"kind": "system", "field_id": "status_category"}},
  "y":       {"agg": "count"},
  "filters": [
    {"ref": {"kind": "system", "field_id": "created"},
     "op": "between", "values": ["2026-01-01", "2026-06-30"]},
    {"ref": {"kind": "field", "field_pk": 3312},
     "op": "in", "values": ["Blocker", "Critical"]}
  ],
  "time_mode": {"kind": "event"},
  "tz": "Asia/Seoul",
  "limit": 30
}
```

| 항목 | 허용값 |
|---|---|
| `bucket` (날짜 필드 전용) | `day` `week` `month` `quarter` `year` → `TRUNC(x, 'DD'\|'IW'\|'MM'\|'Q'\|'YYYY')` |
| `agg` | `count` `count_rows` `sum` `avg` `min` `max` `count_distinct` |
| `op` | `eq` `in` `not_in` `between` `gt` `gte` `lt` `lte` `is_null` `is_not_null` `contains` |

`sum`/`avg`는 대상 ref의 `value_kind='NUM'` 검증을 통과해야 한다. 검증 실패는 400으로 거절하고
SQL을 만들지 않는다.

### 6.3 ref → SQL 변환 (`query_builder.py`)

빌더의 본체는 ref 하나를 SQL 표현식 하나로 바꾸는 함수다.

**`system` + `storage_kind='COLUMN'`** → 조인 없음
```sql
i.status_category
```

**`field` / `unified`** → EAV 조인. **축은 반드시 `LEFT JOIN`이다** (규칙 6)
```sql
LEFT JOIN test_issue_field_value v1
  ON v1.issue_id = i.issue_id
 AND v1.field_pk IN (:p1)          -- unified면 멤버 field_pk 목록
-- 표현식: COALESCE(v1.val_str, '__NULL__')
```

**`unified`일 때만** 값 매핑을 덧붙인다
```sql
LEFT JOIN test_unified_value_member m ON m.field_pk = v1.field_pk
                                AND m.raw_value = v1.val_str
LEFT JOIN test_unified_value       uv ON uv.unified_value_id = m.unified_value_id
-- 표현식: COALESCE(uv.canonical_value, v1.val_str)
```

**값 매핑 테이블을 1단계에서 비워두는 게 안전한 이유가 이 `LEFT JOIN + COALESCE`다.**
매핑이 없으면 원본 값이 그대로 나오고, 나중에 행을 넣으면 즉시 반영된다. 빌더 코드는
바뀌지 않는다.

### 6.4 정확성 규칙 — 놓치면 숫자가 조용히 틀린다

**규칙 1. 필터는 `JOIN`이 아니라 `EXISTS`**

`labels` 같은 다중값 필드를 JOIN으로 필터하면 이슈 하나가 라벨 개수만큼 복제돼 카운트가
부풀려진다.

```sql
AND EXISTS (
  SELECT 1 FROM test_issue_field_value f1
  WHERE f1.issue_id = i.issue_id
    AND f1.field_pk = :p
    AND f1.val_str IN (:v1, :v2)
)
```

축(`GROUP BY`)만 JOIN을 쓴다 — 축에서의 행 증폭은 **의도된 동작**이다. 라벨별 집계는 원래
이슈가 여러 막대에 들어가야 맞다.

**규칙 2. `count`의 기본은 `COUNT(DISTINCT i.issue_id)`**

축이 다중값이면 `COUNT(*)`와 결과가 다르다. 기본을 DISTINCT로 두고, 원할 때만
`"agg": "count_rows"`로 바꾼다.

**규칙 3. `i.deleted_at IS NULL`을 모든 쿼리에 기본 적용**

**규칙 4. 날짜 버킷에만 타임존 변환, 범위 필터는 UTC 원본에** (2.1절 참고)

**규칙 5. `label_column_name`이 있으면 그룹핑 키와 표시 라벨을 분리한다**

```sql
SELECT i.assignee_user_key           AS x,
       MAX(i.assignee_display_name)  AS x_label,
       COUNT(DISTINCT i.issue_id)    AS y
FROM   test_jira_issue i ...
GROUP  BY i.assignee_user_key
```

표시 이름으로 그룹핑하면 동명이인이 한 사람으로 합쳐진다 (3.1절 `TEST_JIRA_FIELD` 참고).

**규칙 6. `NULL`(값 없음)을 버리지 않는다**

축이 EAV 필드일 때 `JOIN`을 쓰면 **그 필드에 값이 없는 이슈가 통째로 사라진다.**
"미분류" 이슈가 100건인데 차트에 안 나오면 사용자는 합계가 왜 안 맞는지 알 수 없다.
축은 `LEFT JOIN`으로 붙이고 표현식을 `COALESCE(v1.val_str, '__NULL__')`로 감싼다.
표시 이름(`(값 없음)`)은 API 응답 계층에서 붙인다.

시스템 필드 축도 같다 — `assignee`가 NULL인 미할당 이슈는 하나의 카테고리로 나와야 한다.

### 6.5 완성 예시 — 이벤트 모드

`프로젝트 12·13, 2026년 상반기 생성, X축 = 커스텀필드 '결함원인', 계열 = 상태 카테고리`

```sql
SELECT COALESCE(v1.val_str, '__NULL__') AS x,
       i.status_category                AS series,
       COUNT(DISTINCT i.issue_id)       AS y
FROM   test_jira_issue i
LEFT   JOIN test_issue_field_value v1
       ON v1.issue_id = i.issue_id
      AND v1.field_pk IN (:p_cause)
WHERE  i.project_id IN (:pr1, :pr2)
AND    i.deleted_at IS NULL
AND    i.created_at >= :from_utc
AND    i.created_at <  :to_utc
GROUP  BY COALESCE(v1.val_str, '__NULL__'), i.status_category
ORDER  BY y DESC
```

시스템 필드 필터가 몇 개 붙든 조인 수가 늘지 않는 것이 하이브리드 구조의 이점이다.
`LEFT JOIN` + `COALESCE`로 '결함원인'이 비어 있는 이슈도 `__NULL__` 막대로 남는다(규칙 6).
`limit`은 여기 붙이지 않고 6.9절의 `OTHER` 합산 패턴으로 감싼다.

### 6.6 과거 시점 차트 (`time_mode: asof`)

```json
{"kind": "asof", "from": "2026-05-01", "to": "2026-08-16", "grain": "day"}
```

빌더가 `TEST_JIRA_ISSUE` 대신 `TEST_ISSUE_FIELD_HISTORY` 경로를 탄다. 필터·계열·프로젝트 범위는
이벤트 모드와 동일하게 적용된다.

#### 스냅샷 시점의 정의

**각 날짜 `D`의 값은 "로컬 시각 기준 `D`가 끝나는 순간", 즉 `D+1일 00:00`의 상태다.**
"그 날의 미완료 이슈 수"라고 하면 대개 하루가 끝난 시점을 뜻하기 때문이다. 오늘은 아직
끝나지 않았지만 마지막 구간의 `valid_to`가 `9999-12-31`이므로 현재 상태가 그대로 나온다.

#### 타임존 — 여기서 조용히 9시간이 밀린다

`valid_from`/`valid_to`는 **UTC**이고 사용자가 보는 날짜는 **로컬**이다. 날짜 CTE의 값을
그대로 비교하면 `2026-05-01 00:00 KST`(= `2026-04-30 15:00 UTC`)를 UTC 자정으로 착각해
경계가 9시간 어긋난다. **CTE에서 로컬 날짜와 UTC 시점을 함께 만든다:**

```sql
WITH days AS (
  SELECT d_local,
         CAST(FROM_TZ(CAST(d_local + 1 AS TIMESTAMP), :tz)
              AT TIME ZONE 'UTC' AS TIMESTAMP) AS t_utc   -- D가 끝나는 순간
  FROM  (SELECT :from_dt + LEVEL - 1 AS d_local
         FROM   dual CONNECT BY LEVEL <= :n_days)
)
SELECT days.d_local               AS x,
       COUNT(DISTINCT i.issue_id) AS y
FROM   days
JOIN   test_issue_field_history h
       ON  h.field_pk   = :f_status_category
       AND h.valid_from <= days.t_utc
       AND days.t_utc   <  h.valid_to
JOIN   test_jira_issue i
       ON  i.issue_id   = h.issue_id
       AND i.project_id IN (:pr1, :pr2)
       AND i.deleted_at IS NULL
WHERE  h.val_str <> 'done'
GROUP  BY days.d_local
ORDER  BY days.d_local
```

`x`로 나가는 것은 `d_local`(사용자가 기대하는 날짜)이고, 조인에 쓰이는 것은 `t_utc`다.
둘을 섞으면 안 된다.

#### 인스턴스 간 asof는 `status_category` 이력을 쓴다

위 쿼리가 `:f_status`가 아니라 `:f_status_category`를 참조하는 것에 주목할 것.
`status` 이력에는 인스턴스마다 다른 **상태 이름**(`완료` / `Done`)이 들어 있어 교차 차트에서
비교할 수 없다. 그래서 `derive_history`가 `status_category`의 이력을 **별도 필드로 함께
생성한다** (5.3절). 이벤트 모드에서 `status_category`가 교차의 열쇠였던 것처럼, asof
모드에서도 같은 역할을 한다.

일별 스냅샷을 물리적으로 쌓지 않고도 임의 과거 날짜를 재현한다.

#### asof 모드에서 쓸 수 없는 필터

이력이 없는 필드로는 과거 시점을 필터할 수 없다. 필터 대상이
`TEST_ISSUE_FIELD_HISTORY`에 없는 필드면, 그 필터는 **현재 값 기준**으로 적용된다
(`TEST_JIRA_ISSUE` / `TEST_ISSUE_FIELD_VALUE` 조인). 이건 의미가 섞이는 지점이므로
**응답에 `filters_applied_as_current` 목록을 함께 반환해** 사용자가 알 수 있게 한다.

### 6.8 보안

식별자(컬럼명)는 **`TEST_JIRA_FIELD.column_name`에서만** 오고, 값은 **전부 바인드 변수**,
집계함수·버킷·연산자는 **enum 매핑**이다. 사용자 입력이 SQL 문자열로 연결되는 경로가 하나도 없다.

### 6.9 성능 가드

- `projects`는 필수 — 빈 값이면 400으로 거절 (전체 스캔 방지)
- 커넥션에 `call_timeout` 설정 (기본 30초)
- `asof`의 `n_days`는 최대 731(2년). 초과하면 400. 날짜 CTE × 이력 행의 조인이므로
  기간이 곧 비용이다. `grain`이 `week`/`month`면 CTE를 주/월 단위로 만들어 행 수를 줄인다

**`limit`은 `FETCH FIRST`로 자르면 안 된다.** 그냥 자르면 나머지가 사라져 합계가 맞지 않고,
사용자는 그 사실을 모른다. 순위를 매긴 뒤 초과분을 `OTHER`로 **합산**한다:

```sql
WITH agg AS (
  SELECT <x_expr> AS x, COUNT(DISTINCT i.issue_id) AS y
  FROM   ... GROUP BY <x_expr>
), ranked AS (
  SELECT x, y, ROW_NUMBER() OVER (ORDER BY y DESC) AS rn FROM agg
)
SELECT CASE WHEN rn <= :lim THEN x ELSE 'OTHER' END AS x,
       SUM(y) AS y
FROM   ranked
GROUP  BY CASE WHEN rn <= :lim THEN x ELSE 'OTHER' END
ORDER  BY y DESC
```

`limit` 기본 100, 최대 1000. 계열(`series`)이 있으면 **축 기준으로만 순위를 매긴다** —
축과 계열의 조합으로 자르면 특정 계열만 통째로 사라진다.

**`OTHER`라는 실제 값이 존재할 수 있다.** 충돌하면 집계가 잘못 합쳐지므로, 라벨은 값으로
쓰이지 않는 문자열(`__OTHER__`)을 쓰고 표시 이름은 API 응답 계층에서 붙인다.

### 7.1 `JiraClient` 프로토콜 — 사외 개발의 축

Jira를 사외에서 띄우지 않기로 했으므로, **파이프라인은 HTTP를 직접 알지 못하게 한다.**
`pipeline/*`은 `JiraClient` 프로토콜만 받고, 구현체를 주입받는다.

```python
class JiraClient(Protocol):
    def get_fields(self) -> list[dict]: ...
    def get_projects(self) -> list[dict]: ...
    def get_statuses(self) -> list[dict]: ...
    def search_issues(self, jql: str, start_at: int, max_results: int,
                      expand_changelog: bool) -> SearchPage: ...
    def get_issue_changelog(self, issue_key: str, start_at: int) -> ChangelogPage: ...
    def get_issue(self, issue_id: str, fields: list[str]) -> dict | None: ...
```

- **`HttpJiraClient`** — 실제 구현. 재시도·백오프·인증·페이징. 사내에서만 실행된다
- **`FakeJiraClient`** — 픽스처를 메모리에 올리고 **JQL의 최소 부분집합**(`project =`,
  `updated >=`, `ORDER BY updated ASC`)만 해석해 페이징을 진짜처럼 흉내낸다

`SearchPage`가 `start_at`/`max_results`/`total`을 그대로 노출하므로, **서버가
`max_results`를 축소하는 상황(A7)도 Fake에서 재현된다.**

### 7.2 `FakeJiraClient`의 시나리오 주입

문서 10장의 파이프라인 코너케이스를 사외에서 재현하는 장치다. 가짜 HTTP 서버 없이
**메서드 호출 사이에 상태를 바꾸는 훅**으로 구현한다.

| 시나리오 | 재현 방법 | 검증 대상 |
|---|---|---|
| 페이징 중 이슈 `updated` 변경 | `on_page(n)` 훅에서 픽스처의 `updated`를 밀어버린다 | 워터마크 겹침이 실제로 막아주는가 (#12) |
| changelog 100개 초과 | `changelog.total > maxResults`인 픽스처 | 보충 호출 경로 (A3) |
| 서버가 `maxResults` 축소 | 요청 100 → 응답 50 | 응답값 기준 페이징 (A7) |
| 프로젝트 간 이동 | 이슈의 `project`/`key`를 바꾸고 `updated` 갱신 | `jira_issue_id` 기준 MERGE (#5) |
| 화이트리스트 밖 이동 | 목록에서 빼고 `get_issue`는 200 반환 | `MOVED_OUT` 판정 (5.6) |
| 삭제 | 목록에서 빼고 `get_issue`는 `None` | `DELETED` 판정 (5.6) |
| 429 / 503 | `raise_on_call(n, status)` | 백오프·재시도 |
| 이력 종점 ≠ 현재값 | changelog 일부를 잘라낸 픽스처 | 현재값 우선 + 경고 (5.3) |

**한계를 분명히 해둔다.** Fake는 HTTP 레이어(헤더·타임아웃·커넥션 재사용·실제 JQL 파서)를
검증하지 않는다. 그 부분은 사내 첫 실행이 첫 테스트다 (11.8절).

## 9. 검증 전략

### 9.1 단위 테스트 (DB 불필요)

- **`parser.py`** — 픽스처 JSON → 기대 dataclass. 4.3절 타입별 값 추출을 전부 커버.
  빈 배열, 값 없음, 앞뒤 공백, 1000바이트 초과 절단 포함
- **`derive_history.py`** — changelog 픽스처 → 기대 구간. **5.3절 경계 조건 표의 6개 항목을
  각각 테스트로 고정한다.** `status_category` 병합(연속 같은 카테고리 → 구간 1개)도 포함
- **`query_builder.py`** — 다음 단계. 착수 시 최소한 이 다섯 개를 스냅샷으로 고정한다:
  1. 다중값 **필터가 `EXISTS`로** 나오는지 (규칙 1)
  2. **축이 `LEFT JOIN` + `COALESCE`**인지 (규칙 6)
  3. **범위 필터에 타임존 함수가 안 씌워지는지** (규칙 4)
  4. `asof` CTE가 `d_local`과 `t_utc`를 **분리**하고 조인에 `t_utc`를 쓰는지 (6.6절)
  5. `label_column_name`이 있는 필드에서 **그룹핑 키와 라벨이 분리**되는지 (규칙 5)

### 9.1.1 파이프라인 시나리오 테스트 (`FakeJiraClient` + 리포지토리 스텁)

7.2절 시나리오 8종을 각각 테스트로 고정한다. **DB가 없으므로 검증 대상은 "무엇을 호출했는가"
까지다.** 예를 들어 페이징 중 `updated`가 바뀌는 시나리오에서, 사외 테스트는
`upsert_issues`에 그 이슈가 두 번 전달되는 것까지 확인하고, **행이 하나로 유지되는지는
사내에서 확인한다.**

시나리오별로 사외/사내 경계가 이렇게 갈린다.

| 시나리오 | 사외에서 검증 | 사내에서 검증 |
|---|---|---|
| 연속 3회 실행 | 두 번째부터 해시 스킵 경로를 타는가 | **행 수 불변** (멱등성) |
| 페이징 중 `updated` 변경 | 겹침 구간이 JQL에 반영되는가 | 이슈가 유실되지 않는가 |
| changelog 100개 초과 | 보충 호출이 발생하는가 | 이력 행이 100개를 넘는가 |
| `maxResults` 축소 | 응답값으로 전진하는가 | 전체 건수가 맞는가 |
| 프로젝트 간 이동 | `MOVED_IN` 분기를 타는가 | 같은 행이 갱신되는가 (새 행이 안 생기는가) |
| 화이트리스트 밖 이동 | `MOVED_OUT`으로 판정하는가 | `delete_reason`이 저장되는가 |
| 삭제 | `DELETED`로 판정하는가 | 상동 |
| 이력 종점 불일치 | 현재값으로 덮고 경고를 남기는가 | 구간이 올바르게 저장되는가 |

**겹침 구간이 살아있는지 확인하는 방법**은 사외에서도 된다 — `OVERLAP`을 0으로 바꾸면
"겹침 구간이 JQL에 반영되는가" 테스트가 실패해야 한다. 실패하지 않으면 그 장치가 아무것도
하고 있지 않다는 뜻이다.

### 9.2 정적 대조 테스트 (DB 불필요)

`db/schema_map.py`가 `db/ddl/*.sql`을 파싱해 만든 `{테이블: {컬럼}}` 사전을 기준으로 검사한다.

- **리포지토리 SQL이 참조하는 모든 테이블이 DDL에 존재하는가**
- **참조하는 모든 컬럼이 해당 테이블에 존재하는가**
- 모든 SQL이 `TEST_` 접두사 테이블만 참조하는가
- 값이 바인드 변수로만 들어가는가 — SQL 문자열에 `f"..."`나 `%` 포매팅이 없는가
- `db/ddl/` 파일에 `VARCHAR2(n)`에 `BYTE`가 빠진 곳이 없는가
- `DEFAULT SYSTIMESTAMP`가 남아 있지 않은가 (`SYS_EXTRACT_UTC(SYSTIMESTAMP)`여야 함)
- 19c 금지 문법(`BOOLEAN`, `IF NOT EXISTS`, 네이티브 `JSON`)이 DDL에 없는가

마지막 세 개는 사외에 DB가 없어 실행으로 잡을 수 없으므로, **문자열 검사로 대신한다.**

### 9.2.1 파이프라인 호출 순서 테스트 (DB 불필요)

리포지토리 함수를 기록용 스텁으로 바꿔치기해 파이프라인의 분기와 순서를 검증한다.
**데이터가 저장되는지는 검증하지 않는다.**

- `sync_issues`가 `upsert_issues` → `upsert_raw` 순서로 부르는가 (FK 순서, spec §5.2)
- `payload_hash`가 같을 때 `touch_synced_at`만 부르고 나머지를 건너뛰는가
- 신규 이슈 수만큼만 `next_issue_ids`를 부르는가 (파싱 실패 시 소진되지 않는가)
- 페이징이 응답의 `max_results`로 전진하는가 (요청값이 아니라 — A7)
- 프로젝트 하나가 실패했을 때 나머지가 계속되고, 실패한 것만 워터마크를 유지하는가
- `full_resync_requested`가 **성공 직후에만** 내려가는가

### 9.3 E2E 검증 (사내)

1. 테스트 Jira 프로젝트 1개를 화이트리스트에 등록 (`is_enabled='Y'`)
2. `python -m jira_dashboard.cli sync --project TEST`
   → `TEST_SYNC_RUN` 성공, 이슈 수가 Jira UI의 JQL 검색 건수와 일치
3. **한 번 더 실행** → 행 수 불변, 워터마크만 전진 (멱등성)
4. Jira에서 이슈 1건의 상태 변경 → 재동기화 → `TEST_ISSUE_CHANGELOG` 신규 행 +
   `TEST_ISSUE_FIELD_HISTORY` 구간 분할 확인
5. `POST /api/chart`로 3종 조회 후 각각 `/api/chart/explain`으로 SQL 확인, Jira UI 필터
   결과와 대조:
   - 시스템 필드 축 — `status_category`별 건수
   - 커스텀 필드 축 — EAV 경로
   - `asof` 모드 — 최근 30일 일별 미완료 건수
6. **타임존 검증** — 로컬 23:00에 생성한 이슈가 `bucket=day` 차트에서 **그 날**에 잡히는지
   확인한다. UTC 자정 처리가 틀리면 다음 날로 밀린다 (2.1절)
7. **asof와 현재 시점의 일치** — `asof`의 마지막 날 값과 이벤트 모드의 현재 값이 같아야 한다.
   다르면 이력 파생에 구멍이 있다는 뜻이다 (5.3절 마지막 경계 조건)

## 11. 로컬 개발 환경과 사내 반입

Jira와 Oracle이 모두 사내에만 있고 **데이터 반출이 불가능하다.** 목표를 "사외에서 100%
검증"으로 잡으면 실패한다. 실제 목표는 이것이다.

> **검증 가능한 것은 사외에서 전부 끝내고, 불가능한 것은 사내 첫날 30초 안에 드러나게 한다.**

리스크를 둘로 나누면 대응이 갈린다.

| 리스크 | 사외에서 | 근거 |
|---|---|---|
| **DB 스키마 정합성** — 테이블·컬럼 이름 일치 | **정적으로 잡는다** | DDL 파일이 곧 진실. SQL을 대조한다 (11.2절) |
| **DB 실행** — MERGE 멱등성, 제약조건, LOB, 시퀀스 | **없앨 수 없다** | 실행해봐야 안다 |
| **Jira API** — 응답 구조, 페이징, changelog 정렬 | **없앨 수 없다** | 픽스처는 결국 4.0절 가정을 구현한 것일 뿐 |

사외에 Oracle을 두지 않기로 한 결과, **DB 실행 리스크가 사내로 옮겨간다.** 이건 의식적인
교환이다 — 환경 구축 비용(이미지 7GB, 첫 기동 20분, 계정·라이선스 동의)을 아끼는 대신,
`MERGE` 문이 실제로 도는지를 사내 첫 실행에서 확인한다. 그래서 11.7절 런북의 멱등성
확인 단계가 **선택이 아니라 필수**가 된다.

데이터는 못 가져와도 **테스트 하네스는 가져갈 수 있다.** 사내에서 실 API를 캡처해 사내에
픽스처를 만들고, 사외에서 통과시킨 **같은 테스트 스위트**를 사내 실데이터로 재실행한다.

### 11.1 DDL은 사내에서 사람이 실행한다

**사외에 Oracle을 두지 않는다.** DDL이 16개 테이블 + 뷰 1개 + 시퀀스 1개로 단순하고,
`TEST_` 접두사 덕분에 일괄 삭제·재생성이 SQL 한 블록으로 끝나기 때문이다. 마이그레이션
러너 같은 자동화는 이 규모에 과잉이다.

대신 **적용 절차를 문서로 고정한다.** `db/ddl/` 파일을 번호순으로 실행하는 것이 전부다.

| 순서 | 파일 | 담긴 객체 (spec 절) |
|---|---|---|
| 1 | `01_catalog.sql` | `TEST_JIRA_INSTANCE`, `TEST_JIRA_PROJECT`, `TEST_JIRA_FIELD`, `TEST_JIRA_PROJECT_FIELD` (§3.1) |
| 2 | `02_unified.sql` | `TEST_UNIFIED_*` 4개 + `TEST_V_UNIFY_CANDIDATE` (§3.2) |
| 3 | `03_issue.sql` | `TEST_SEQ_ISSUE_ID`, `TEST_JIRA_ISSUE`, `TEST_ISSUE_FIELD_VALUE` (§3.3) |
| 4 | `04_history.sql` | `TEST_ISSUE_CHANGELOG`, `TEST_ISSUE_FIELD_HISTORY` (§3.4) |
| 5 | `05_raw.sql` | `TEST_ISSUE_RAW`, `TEST_CHANGELOG_RAW` (§3.5) |
| 6 | `06_ops.sql` | `TEST_SYNC_WATERMARK`, `TEST_SYNC_RUN` (§3.6) |

**번호 순서가 곧 FK 의존 순서다.** 특히 `02_unified.sql` 안에서도
`TEST_UNIFIED_VALUE_MEMBER`가 `TEST_UNIFIED_FIELD_MEMBER`와 `TEST_UNIFIED_VALUE`를 복합
FK로 참조하므로 파일 내부 순서까지 지켜야 한다.

```bash
# 사내에서, sqlplus 또는 원하는 SQL 클라이언트로
@db/ddl/01_catalog.sql
@db/ddl/02_unified.sql
@db/ddl/03_issue.sql
@db/ddl/04_history.sql
@db/ddl/05_raw.sql
@db/ddl/06_ops.sql
```

**갈아엎을 때는** `db/ddl/drop_all.sql`(2.3절)을 먼저 실행하고 위를 다시 돌린다.
접두사 기반이라 테이블이 늘어도 스크립트를 고칠 필요가 없다.

DDL 파일에 버전 관리나 적용 이력 테이블을 두지 않는다. 대신 **`doctor --db`가 DDL 파일과
실제 스키마를 대조**해 어긋난 것이 있으면 알려준다(11.5절). 자동으로 고치지는 않는다 —
스키마 변경은 사람이 의식하고 해야 하는 일이다.

### 11.2 DDL↔SQL 정적 대조 — DB 없이 잡을 수 있는 것

사외에 DB가 없으면 리포지토리의 `MERGE` 문 20여 개가 **한 번도 실행되지 않은 채** 반입된다.
가장 흔한 실패는 **컬럼명 오타와 테이블명 불일치**이고, 이건 DB 없이도 잡힌다.

`db/schema_map.py`가 `db/ddl/*.sql`을 파싱해 `{테이블: {컬럼, ...}}` 사전을 만든다.
테스트는 리포지토리 모듈의 모든 SQL 문자열을 훑어 참조된 테이블·컬럼이 사전에 있는지 본다.

```
잡히는 것                                   못 잡는 것
─────────────────────────────────────      ─────────────────────────────────
존재하지 않는 테이블 참조                     MERGE 문의 문법 오류
존재하지 않는 컬럼 참조                       실행계획 / 성능
DDL에서 이름을 바꿨는데 SQL은 그대로            멱등성 (MERGE 키가 맞는가)
TEST_ 접두사 누락                            제약조건이 실제로 막아주는가
바인드 변수 대신 문자열 연결                    LOB 적재, 시퀀스 채번
```

**왼쪽은 사외에서 전부 잡고, 오른쪽은 사내 첫 실행이 첫 테스트다.** 이 경계를 분명히 아는
것이 중요하다 — 정적 대조가 통과했다는 것이 "SQL이 돈다"는 뜻은 아니다.

파서는 완전한 SQL 파서가 아니어도 된다. `CREATE TABLE` 블록에서 컬럼 정의만 뽑고,
리포지토리 SQL에서는 정규표현식으로 `TEST_\w+` 토큰과 `:바인드` 이름을 뽑는 수준으로 충분하다.
**의존성을 추가하지 않는다.**

정적 대조가 성립하려면 리포지토리가 지켜야 할 규칙이 하나 있다.

> **SQL은 모듈 수준 상수나 함수 안의 리터럴 문자열로 둔다.** 조각을 런타임에 이어 붙여
> 만들면 정적으로 읽을 수 없다. 바인드 목록처럼 개수가 가변인 부분만 예외로 하고,
> 그 경우 테이블·컬럼 이름은 리터럴에 남긴다.

### 11.3 테스트 계층

| 계층 | 필요 인프라 | 커버 | 사외에서 |
|---|---|---|---|
| 단위 | 없음 | `parser`, `derive_history`, `fake`, `doctor` 판정 로직 | **완전 검증** |
| 정적 대조 | 없음 | DDL↔SQL 테이블·컬럼 일치, 바인드 변수 사용 | **완전 검증** |
| 파이프라인 | `FakeJiraClient` + **가짜 DB 계층** | 호출 순서·분기 로직 | **부분 검증** |
| DB 실행 | 실 Oracle | MERGE 멱등성, 제약조건, LOB, 시퀀스, 실행계획 | **불가 — 사내 전용** |
| 계약 | 실 Jira (읽기 전용) | 4.0절 A1~A12 | **불가 — 사내 전용** |

세 번째 계층의 "가짜 DB 계층"은 SQL을 해석하지 않는다. **리포지토리 함수를 기록용
스텁으로 바꿔치기해**, 파이프라인이 올바른 순서로 올바른 인자를 넘기는지만 본다.
예를 들어 `sync_issues`가 `upsert_issues` 다음에 `upsert_raw`를 부르는지(FK 순서),
해시가 같을 때 `touch_synced_at`만 부르고 나머지를 건너뛰는지를 검증한다.
**데이터가 실제로 저장되는지는 검증하지 않는다.**

테스트는 **픽스처 디렉터리를 파라미터로 받는다.** 사외에서는 `fixtures/synthetic/`,
사내에서는 `capture`가 만든 `fixtures/captured/`로 **같은 스위트를 재실행**한다.
사내 실데이터로도 통과하면 그때 끝난 것이다.

`fixtures/captured/`는 **`.gitignore`에 넣는다.** 반출 금지 데이터가 사외로 흘러나가는
경로를 원천 차단한다.

### 11.4 오프라인 wheel 번들

사내 Git 단방향 반입이고 사내에 PyPI 접근이 없다고 가정한다. 사내 서버가 **Python 3.12 +
같은 리눅스 계열**이므로 사외에서 받은 wheel이 그대로 동작할 가능성이 높다.

```bash
pip download -r requirements.txt -d vendor/ \
    --only-binary=:all: --python-version 3.12 --platform manylinux2014_x86_64
```

사내에서:
```bash
pip install --no-index --find-links vendor/ -r requirements.txt
```

**`oracledb`를 thin 모드로 고른 것이 여기서 값을 한다** — 순수 Python이라 Instant Client
설치나 네이티브 컴파일이 필요 없다. 반입 대상이 wheel 몇 개로 끝난다.

의존성을 최소로 유지한다: `oracledb`, `httpx`, `pydantic`(설정), `pytest`+`pytest-asyncio`.
`--platform`을 지정하면 순수 Python 패키지도 `--only-binary`가 필요하므로, 위 명령이
실패하는 패키지는 목록에서 빼는 것을 먼저 검토한다.

### 11.5 `doctor` — 가정을 실행 가능한 검사로

4.0절의 A1~A12와 2.4절 DB 전제를 **읽기 전용 명령 하나**로 확인한다. 사내 첫날 가장 먼저
실행한다.

```
cli doctor --db      Oracle 전제 검사
cli doctor --jira    Jira API 계약 검사 (읽기 전용)
```

**`doctor --db`**

| 검사 | 실패 시 |
|---|---|
| 버전이 19c인가 | 상위 버전이면 문법 전제 재검토 |
| `max_string_size` = `STANDARD` | `EXTENDED`면 컬럼 폭 재검토 (2.4절) |
| `Asia/Seoul` 타임존 파일 존재 | 버킷팅 불가 → 오프셋 방식으로 폴백 |
| `NLS_CHARACTERSET`, `db_block_size` | 값만 출력 (기록용) |
| `CREATE TABLE`/`SEQUENCE`/`VIEW` 권한 | DDL 실행 실패 예고. **DDL을 돌리기 전에 확인한다** |
| 테이블스페이스 쿼터 여유 | 원본 보관 3~6GB를 감당하는가 |
| 기존 `TEST_` 객체 목록 | 남아 있는 것이 있으면 알려준다 |
| **DDL 파일 ↔ 실제 스키마 대조** | `db/ddl/*.sql`이 정의한 테이블·컬럼이 실제로 있는가. 어긋나면 DDL 재적용이 필요하다 |

**`doctor --jira`** — A1~A12를 각각 실호출로 확인하고 **PASS/FAIL과 실측값**을 출력한다.

```
A4  changelog 정렬 방향          FAIL  내림차순(최신 우선)으로 응답함
    → 영향: 구간 테이블이 뒤집힘. sync_issues 보충 호출과
            derive_history 정렬을 수정할 것 (5.2, 5.3절)
```

이런 출력이 나오는 것이 이 도구의 목적이다. **가정이 틀렸다는 사실을 데이터가 잘못 쌓이기
전에, 문서의 어느 절을 고쳐야 하는지와 함께 알려준다.**

### 11.6 `capture` — 사내 픽스처 생성

읽기 전용으로 실 응답을 받아 `tests/fixtures/captured/`에 저장한다. **사내에서만 실행하고
사내에만 남는다.**

```
cli capture --project TEST --limit 200
```

저장 대상: `/field`, `/project`, `/status` 응답 전체와 `search` 응답 몇 페이지
(`expand=changelog` 포함), changelog 100개 초과 이슈 1건.

`--anonymize` 옵션을 만들어 두되 **기본값은 끔**이다. 반출이 금지된 상황에서 익명화 옵션이
있으면 "익명화했으니 가져가도 되겠지"라는 판단을 부르기 쉽다. 익명화는 사내 보관 데이터의
가독성 조절용이지 반출 허가가 아니다.

### 11.7 사내 첫날 런북

순서가 중요하다. **읽기 전용 검사를 통과한 뒤에 DDL을 돌리고, DDL이 끝난 뒤에 코드를 돌린다.**

```
 1. pip install --no-index --find-links vendor/ -r requirements.txt
 2. cli doctor --db --skip-schema     읽기 전용. 버전·권한·타임존·쿼터만 본다
                                      (테이블이 아직 없으므로 스키마 대조는 건너뛴다)
 ────── 권한이 부족하면 여기서 멈춘다 ──────
 3. @db/ddl/01_catalog.sql … 06_ops.sql        사람이 순서대로 실행 (11.1절)
 4. cli doctor --db                   이제 스키마 대조까지 포함해 전부 통과해야 한다
 5. cli doctor --jira                 읽기 전용. A1~A12 결과를 기록
 ────── FAIL이 있으면 사외로 돌아가 고친다 ──────
 6. cli capture --project TEST --limit 200
 7. JIRA_FIXTURES=captured pytest     사외 스위트를 실데이터로 재실행
 8. cli sync --project TEST --dry-run 파싱만, DB 쓰기 없음
 9. cli sync --project TEST           첫 실제 수집 — SQL이 처음 실행되는 순간
10. cli sync --project TEST           2회차 — 행 수 불변(멱등)
11. cli sync --project TEST           3회차 — 동일
12. 이슈 1건 상태 변경 후 재동기화      changelog 신규 행 + 구간 분할 확인
```

**9단계가 이 프로젝트에서 가장 위험한 순간이다.** 사외에 DB가 없었으므로 모든 `MERGE`·`INSERT`
문이 여기서 처음 실행된다. 실패하면 대개 원인이 셋 중 하나다.

| 증상 | 원인 | 확인 |
|---|---|---|
| `ORA-00904: invalid identifier` | 컬럼명 오타 | 정적 대조를 통과했다면 파서가 놓친 케이스다. `db/schema_map.py`를 고친다 |
| `ORA-00001: unique constraint violated` | MERGE의 `ON` 절 키가 잘못됨 | 그 테이블의 UNIQUE 제약과 `ON` 절을 대조한다 |
| `ORA-02291: integrity constraint` | 적재 순서가 FK를 위반 | spec §5.2의 6단계 순서를 다시 확인한다 |

**10~11단계를 건너뛰지 않는다.** 멱등성은 사외에서 전혀 검증되지 않았고, 깨져 있으면
행이 매 배치마다 늘어난다. 2·3회차의 행 수가 1회차와 같은지 반드시 눈으로 확인한다.

```sql
SELECT 'issue' t, COUNT(*) c FROM TEST_JIRA_ISSUE UNION ALL
SELECT 'eav',     COUNT(*)   FROM TEST_ISSUE_FIELD_VALUE UNION ALL
SELECT 'chglog',  COUNT(*)   FROM TEST_ISSUE_CHANGELOG UNION ALL
SELECT 'history', COUNT(*)   FROM TEST_ISSUE_FIELD_HISTORY;
```

5단계에서 FAIL이 나오면 **코드를 고치고 사외 테스트를 다시 통과시킨 뒤 반입한다.**
사내에서 즉석으로 고치면 사외 테스트와 어긋나고, 단방향 반입이라 되돌리기 어렵다.

### 11.8 사외에서 검증할 수 없는 것 (인정하고 넘어가는 목록)

사외에 Oracle을 두지 않기로 해서 이 목록이 길어졌다. **길어진 것을 아는 것이 중요하다.**

| 항목 | 왜 불가능한가 | 사내에서 언제 드러나나 |
|---|---|---|
| DDL이 실제로 실행되는가 | Oracle이 없다 | 런북 3단계 |
| 제약조건이 실제로 막아주는가 (`CK`, 복합 FK) | 상동 | 런북 9단계 (또는 영원히 — 위반 데이터가 안 들어오면 모른다) |
| `MERGE` 문의 문법과 `ON` 절 키 | 상동 | 런북 9단계 |
| **멱등성** (연속 실행에 행 수 불변) | 상동 | 런북 10~11단계 |
| BLOB 적재 (`setinputsizes`, gzip) | 상동 | 런북 9단계 |
| 시퀀스 채번 (`CONNECT BY LEVEL`) | 상동 | 런북 9단계 |
| `drop_all.sql`의 `ESCAPE` 동작 | 상동 | 처음 갈아엎을 때 — **남의 테이블이 지워지면 되돌릴 수 없다** |
| 인덱스가 실제로 쓰이는가 | 실데이터가 없다 | 첫 전체 수집 |
| 사내 Oracle의 권한·쿼터·타임존 파일 | 환경이 다르다 | `doctor --db` (런북 2단계) |
| 4.0절 A1~A12 전부 | 실 Jira가 없다 | `doctor --jira` (런북 5단계) |
| 실제 JQL 파서 동작 | Fake는 부분집합만 해석 | `sync --dry-run` (런북 8단계) |
| HTTP 레이어 (타임아웃·프록시·커넥션) | Fake가 HTTP를 안 탄다 | 첫 `sync` (런북 9단계) |

`drop_all.sql` 항목이 특히 위험하다. `ESCAPE '\'`를 빠뜨리면 `_`가 와일드카드가 되어
`TESTX...` 같은 남의 테이블까지 지우는데, **사외에서 이걸 실행해볼 수 없다.**
사내에서 처음 돌릴 때는 반드시 삭제 대상을 먼저 조회해 눈으로 확인한다.

```sql
-- drop_all.sql 을 돌리기 전에 이것부터
SELECT table_name FROM user_tables WHERE table_name LIKE 'TEST\_%' ESCAPE '\';
```

목록에 `TEST_`로 시작하지 않는 것이 하나라도 있으면 스크립트를 멈추고 조건을 다시 본다.

| **UI** | 1단계 범위 밖. 쿼리 API가 안정화된 뒤 별도 기획한다 |
